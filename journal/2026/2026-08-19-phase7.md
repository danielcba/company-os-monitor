# Journal — 2026-08-19 (Fase 7)

## Theme

Fase 7 del frontend COS-Monitor: vista Anomalies con las desviaciones
detectadas reales del pipeline. Se añade al API Gateway el endpoint READ
`GET /api/v1/tenants/{tenant_id}/anomalies` (paginado, filtrable por
`anomaly_class`, tenant scope) y su detalle
`GET /api/v1/tenants/{tenant_id}/anomalies/{anomaly_id}` con el **desglose de
context** (el Active Context sobre el que se midió la desviación, resuelto
desde la tabla canónica `contexts` vía `context_id`), y el producto web lo
renderiza como tabla de desviaciones con `deviation_score` y
`tolerance_threshold`, más un drawer con el detalle y el contexto fuente.

El frontend sigue siendo capability externa (ADR-0002): representa Anomaly
mostrando la desviación cuantificada, nunca una explicación causal (P4 — las
explicaciones de causa son de Hypothesis; ningún claim causal aparece en esta
vista), y el contenido de una detección es inmutable (P1) — la anomalía no
tiene flag de ciclo de vida (`is_active` no existe en `anomalies`). Todo pasa
por el Gateway (R3).

## Observations & Insights

- **La anomalía no tiene descripción ni flag de lifecycle**: el esquema
  canónico `anomalies` solo persiste la desviación cuantificada
  (deviation_score, tolerance_threshold, anomaly_class, detected_at) sobre
  su context/pattern de origen; la vista no inventa `is_active` ni
  `description` (P1) — a diferencia de Patterns, no hay badge
  active/superseded ni texto descriptivo.
- **0 anomalies reales = empty state honesto**: el detector
  (`apps/services/anomaly-service`) persiste solo cuando la desviación
  supera el umbral sobre un pattern real, y el tenant sandbox no tiene
  patterns con apoyo suficiente aún (Fase 6). La vista muestra "No anomalies
  yet" sin fabricar datos (P1).
- **P4 aplicado al UI**: el drawer explica que la anomalía es una desviación
  medible y que la causa pertenece a Hypothesis; no hay claims causales.

## Decisions & Trade-offs

- **Filtros por facets reales y no por lista fija** (como Fases 3–6): el UI
  no inventa opciones; solo muestra lo que el tenant tiene de verdad.
- **El detalle de context usa `_context_payload`** del `ContextReadStore`: no
  se duplica la lógica de serialización; el desglose queda consistente con la
  Fase 5.
- **Restauración de los métodos READ de Fases 2–6 en `service.py`**: el
  gateway volvió a quedar íntegro (todos los endpoints READ con scope check)
  antes de añadir anomalies; se verificó con los 105 tests y smoke live.
- **Tabla con context id corto (8 chars)** en vez de resolver el contexto en
  el listado: el listado se mantiene como lectura pura de `anomalies` (los
  desgloses se resuelven solo en el drawer, como en las fases anteriores).
