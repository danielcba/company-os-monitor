# Journal — 2026-08-17 (Sprint 12 — Multi-tenant + Auth + RBAC (Decision Authority — Capacidad Externa))

## Theme

Sprint 12 implementa **Multi-tenant + Auth + RBAC** sobre el flujo cognitivo completo: el **user-service** (login + JWT con rol/tenant) y el **API Gateway** (enforcement del Cognitive Boundary, R3) cierran el bloque **Q1** del roadmap (pipeline completo + autoridad + boundary). Ambos son capacidades EXTERNAS NO-canónicas (**ADR-0002**): autorizan y protegen el acceso al flujo canónico, NUNCA producen juicios cognitivos y NUNCA ejecutan el pipeline (la ejecución real queda en el ciclo canónico de cada servicio). El RBAC se modela como **Decision Authority binding** (core-concept decision: *the commitment authority under which a Decision was taken*), mapeando las decisiones a usuarios reales (`authority_id` → `users.id`). Roles según docs/04: viewer, operator, admin, superadmin. El gate de calidad: ninguna conclusión/acción influye el sistema sin autoridad explícita verificable (R3/R5); un viewer no puede ni leer lo de otro tenant ni commitar nada.

## Discoveries

- **`passlib 1.7.4` es incompatible con `bcrypt>=4.1`**: `passlib.handlers.bcrypt` importa `bcrypt.__about__.__version__`, atributo eliminado en bcrypt 4.x → `AttributeError`. Solución: NO usar passlib; usar el paquete `bcrypt` directamente (`bcrypt.hashpw`/`checkpw`), que ya está instalado vía `passlib[bcrypt]`. Documentado para no reintroducir passlib.
- **asyncpg + INSERT ... RETURNING con columna NULL en users**: el primer intento del INSERT omitía `password_hash` en la cláusula RETURNING implícita de la fila insertada (mismatch de aridad) → se fija `RETURNING id, tenant_id, email, password_hash, name, role, is_active, created_at, updated_at` con `password_hash` bindeado explícito.
- **`PLR0913`/`TRY003` en la access layer**: `JwtService.__init__`/`create_token`/`UserStore.create_user` (6-7 args de configuración/claves) y los `raise` con mensaje declarativo → suprimidos con `# noqa` específico como ya hace `libs/procedural_memory/pattern_library.py`; sin apagar la regla global.
- **`e2e live de acciones NUNCA ejecuta**: el gateway responde `{authorized: true, ..., "note": "validated by the Cognitive Boundary (R3); execution happens in the canonical service cycle, not here"}` — diseño intencional ADR-0002 (capacidad externa no ejecuta el pipeline).

## Decisions

- **RBAC modelado como Decision Authority binding, no como "tabla de permisos"**: roles (viewer/operator/admin/superadmin) determinan qué autoridad puede ejecutar qué acción; `authority_id` de las Decisiones (Sprint 10) ahora referenciable a usuarios reales. R3 se respeta: percepción/razonamiento nunca ejecutan acción sin autorización explícita; el gateway enforza el flujo canónico.
- **user-service y gateway como capacidades externas NO-canónicas (ADR-0002)**: autorizan/protegen, nunca producen juicios cognitivos ni ejecutan el pipeline. Garantía estructural testada: `libs/access` y ambos servicios no importan `libs.perception/reasoning/learning/procedural_memory/action`.
- **Estrategia refresh stateless**: access + refresh firmados con exp propia; sin tabla `refresh_tokens` ni token store en Redis (menos superficie de estado; revocación como fase futura, no requerida en el sprint).
- **JWT HS256 en dev, RS256 en prod**: default en código HS256 con `JWT_SECRET_KEY`; `.env.example` documenta la pareja de claves para `JWT_ALGORITHM=RS256` (refleja la política del sprint: dev simple, prod firmado asimétrico). Claims nunca confiables por sí solos: verificación de firma + exp + tipo en cada decode.
- **`users` MUTABLE por diseño (sin trigger P1)**: dato externo de identidad (crear/inactivar usuarios, resetear password), no contenido cognitivo; `is_active` para deshabilitar acceso sin borrar trazabilidad.
- **El gateway NUNCA ejecuta**: `POST /api/v1/actions/{action}` valida autoridad + boundary + confidence y responde el binding; la ejecución real es el ciclo canónico de cada servicio. Así la capacidad externa no se convierte en otro atajo del pipeline.
- **Confidence obligatoria en propose/commit (R4)**: el gateway rechaza la acción sin `confidence_id`/`confidence_score` (400) — ninguna conclusión influye acción sin confianza calibrada.
- **Puertos/env propios**: `USER_HEALTH_PORT=8099`, `GATEWAY_HEALTH_PORT=8100` (fuera del rango 8090-8098 del pipeline), `JWT_*`, `GATEWAY_SERVICE_HEALTH` (override). No se reutilizaron nombres previos.
- **Sesión EVALUADA al inicio** (355 tests previos verdes). Sin cambios a prompts previos ni journals previos. La sandbox quedó con solo el admin seed (usuarios de prueba eliminados) y sin datos cognitivos tocados.

## Reflection

El sprint respeta la frontera del concepto y del producto: la autenticación/autorización es una capacidad EXTERNA no-canónica (ADR-0002) que da **authority binding** auditable a las decisiones — no una fase del razonamiento. El RBAC se modela como Decision Authority (rol + tenant + riesgo), no como tabla de permisos suelta: cada `commit`/`execute` queda atado a un usuario real y verificable (R5), y el gateway enforza el Cognitive Boundary (R3) con reglas puras testeadas celda a celda. La separación es estructural y verificada por tests que impiden que la capa de acceso importe el pipeline. R1 se mantiene en el producto: cada servicio canónico sigue haciendo exactamente una capacidad; auth/RBAC no razona ni decide ni ejecuta. La política de citación canónica se respetó: P1, R3, R4, R5, ADR-0001/ADR-0002, conceptos del marco (decision/authority); trazabilidad/objetividad/provenance descritas de forma factual, sin números de regla inventados.
