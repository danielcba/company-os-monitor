# Journal — 2026-08-19 (Fase 6)

## Theme

Fase 6 del frontend COS-Monitor: vista Patterns con las regularidades
detectadas reales del pipeline. Se añade al API Gateway el endpoint READ
`GET /api/v1/tenants/{tenant_id}/patterns` (paginado, filtrable por
`pattern_type`/`is_active`, tenant scope) y su detalle
`GET /api/v1/tenants/{tenant_id}/patterns/{pattern_id}` con el **desglose de
context** (el Active Context sobre el que se detectó la regularidad, resuelto
desde la tabla canónica `contexts` vía `context_id`), y el producto web lo
renderiza como tabla de regularidades con su strength_measure y frecuencia,
más un drawer con la descripción completa y el contexto fuente.

El frontend sigue siendo capability externa (ADR-0002): representa Pattern
mostrando regularidad como estructura, nunca como causa (P4 — las
explicaciones de causa son de Hypothesis; ningún claim causal aparece en esta
vista), y el contenido de una detección es inmutable (P1) — solo el flag
`is_active` es de ciclo de vida. Todo pasa por el Gateway (R3).

## Observations & Insights

- **0 patterns reales = empty state honesto**: el detector
  (`apps/services/pattern-service`) solo persiste regularidades cuyo support
  medido supera el umbral de la librería (`min_occurrences` 3 para
  capacity_risk/service_failure, 2 para auth_compromise, etc.), y el tenant
  sandbox solo tiene 1–2 activaciones por mental model. La vista muestra
  "No patterns yet" sin fabricar datos (P1) — igual que `quality_class=Q2` en
  Fases 3–4.
- **El desglose de patterns es context, no evidence**: a diferencia de
  evidence (→ observations) y contexts (→ evidence), `patterns` no tiene
  columna de ids; su Input canónico es el Active Context (`context_id`), y el
  detalle lo resuelve reusando `ContextReadStore._context_payload`.
- **El esquema real no tiene quality_class/weight en patterns**: la medida de
  soporte es `strength_measure` (support/frequency/p-value, NUMERIC(5,4)) +
  `frequency`; la vista usa esos campos canónicos y no inventa badges Q1–Q4.
- **P4 aplicado al UI**: el drawer explica que un Pattern describe estructura
  y que la causa pertenece a Hypothesis; la descripción real ("Regularidad
  detectada") se muestra tal cual, sin claims causales añadidos.

## Decisions & Trade-offs

- **Filtros por facets reales y no por lista fija** (como Fases 3–5): el UI
  no inventa opciones; solo muestra lo que el tenant tiene de verdad.
- **El detalle de context usa `_context_payload`** del `ContextReadStore`: no
  se duplica la lógica de serialización; el desglose queda consistente con la
  Fase 5.
- **Tabla con context id corto (8 chars) en vez de resolver el contexto en el
  listado**: el listado se mantiene como lectura pura de `patterns` (los
  desgloses se resuelven solo en el drawer, como en las fases anteriores).
