# Journal — 2026-08-20 (QA data re-seed)

## Theme

Re-seed de datos QA del tenant sandbox (pendiente desde Fase 6): la cadena
cognitiva estaba atascada en vacío — patterns=0, anomalies=0 (el único anomaly
era residuo de test en un tenant fantasma), hypotheses/confidence/
recommendations/decisions=0. Se publica un escenario de **presión de backup**
como observaciones inmutables (P1) y se deja que el pipeline haga TODO el resto:
pattern → anomaly → hypotheses → confidence → recommendations → decisions →
reports.

El seed es un script de replay (`scripts/qa_seed.py`): publica al Observation
Bus (Redis) lo que los agentes habrían capturado durante un incidente — 4
batches de backup-failure, cada uno desde un source DISTINTO para que el
organizer produzca Evidence determinista nueva por batch y el activator genere
una activación de Contexto por batch (supersede). El script NUNCA escribe una
conclusión, juicio ni confidence: solo observaciones (P1); todo lo downstream
lo calculan los servicios canónicos.

## Observations & Insights

- **El cuello de botella real era la formación de patrones**: sin ≥3
  activaciones por scope no hay patrón; sin patrón no hay anomalía (la
  detección es relativa, nunca absoluta); sin anomalía no hay hypotheses → la
  cadena entera se apaga aguas abajo. Un solo batch de observaciones no cambia
  nada: hace falta que el contexto se re-active con Evidence NUEVA (el id
  determinista del contexto deriva de los evidence_ids, así que cada evidence
  nueva genera una activación que supersede a la anterior).
- **El seed se mantiene dentro de la frontera canónica**: publicar
  observaciones es el input inmutable del sistema (como haría un agente); las
  conclusions downstream (patrones, anomalías, hipótesis, confidence,
  recomendaciones, decisiones, reportes) las producen los servicios canónicos
  con sus librerías declarativas — nada se inyecta ni se fabrica.
- **El escenario backup-pressure** engancha de punta a punta porque cada etapa
  tiene cobertura declarativa para ese scope: organizer (backup_failure_rule),
  mental model capacity_risk, templates de hypothesis (3), tolerance
  (schedule_deviation_capacity_risk), action space backup, decision policy
  backup (threshold 0.75) y renderer executive con top_decisions.
- **Confianza alta y honesta**: C_final ≈ 0.999 porque S≈1 (4 evidence Q1 de
  peso 0.88 que la hipótesis explica) y C=1 (explica todo el scope), con el
  factor 1−ECE=1.0 documentado (sin historial de outcomes: primera pasada,
  ECE 0). El desglose en la UI muestra la justificación verbatim.
- **El flujo sigue vivo**: el linux-agent continúa capturando observaciones
  reales cada 60s (observations crece solo); el re-seed es seguro de re-ejecutar
  (las evidence son deterministas por observación; un segundo run añade una
  nueva onda de evidencia).

## Decisions & Trade-offs

- **Script de replay en vez de SQL directo**: publicar al bus respeta la
  frontera (observations append-only vía el canal de ingesta canónico) y deja
  que el collector/consumer haga la persistencia y organización. Insertar
  filas a mano en tablas canónicas habría roto el contrato de ingesta.
- **Un source distinto por batch**: la evidencia organizada es determinista
  por observation_ids; con un source nuevo por batch, cada batch produce una
  fila de Evidence distinta y el contexto se re-activa (supersede) — la clave
  para que el stream de contextos crezca y el patrón se forme.
- **Progresión por polling** en vez de sleeps fijos: robusta a la cadencia
  real de los ciclos (collector 1s, activator 30s, resto 60s).
- **No se tocó código de servicios ni frontend**: el re-seed solo añade un
  script de QA; los tests (gateway 164, web 84) siguen verdes sin cambios.
