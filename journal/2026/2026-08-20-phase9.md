# Journal — 2026-08-20 (Fase 9)

## Theme

Fase 9 del frontend COS-Monitor: vista Confidence con las estimaciones de
fiabilidad calibradas reales del pipeline. Se añade al API Gateway el endpoint
READ `GET /api/v1/tenants/{tenant_id}/confidence` (paginado, filtrable por
`target_type` hypothesis|recommendation|decision, ordenable por `computed_at`,
tenant scope) y su detalle `GET /api/v1/tenants/{tenant_id}/confidence/{confidence_id}`
con el **desglose del target evaluado**: para un target `hypothesis` se reutiliza
el desglose de Hypotheses (anomalies + Active Contexts, resueltos desde las
tablas canónicas); para `decision`/`recommendation` se devuelve el payload
canónico de esos conceptos de la capa futura de Action.

Confidence es la capacidad de calibrar la fiabilidad de los juicios del
pipeline (Learning · Calibrate). Es **computada, no intuida** (P5): cada fila
de la tabla canónica `confidence_scores` registra el C_final con su justificación
de primera clase — soporte evidencial S, coherencia explicativa C, el factor de
calibración (1 − ECE), el coeficiente α y la estimación de error ECE. Un score
de confianza es una estimación calibrada de fiabilidad, no "la probabilidad de
que la hypothesis sea cierta". El contenido es **totalmente inmutable** (P1):
el trigger `confidence_content_immutable_trigger` bloquea todo UPDATE/DELETE, de
modo que una recalibración con distintos inputs es una fila nueva, nunca una
actualización. Todo pasa por el Gateway (R3). La calibración y el Action Layer
(Recommendation → Decision) son fases futuras (R4); esta fase solo expone la
lectura canónica.

## Observations & Insights

- **Confidence es la primera vista donde el número importa con semántica (P5)**:
  a diferencia de las vistas anteriores (que muestran hechos, estructura y
  desviaciones), Confidence presenta la fiabilidad calibrada de un juicio. La
  clave es la justificación de primera clase: el número solo se entiende con
  S, C, ECE, α y la fórmula documentada. La UI lo muestra todo, verbatim, sin
  inventar un porcentaje de "verdad".
- **P1 se aplica en su forma más estricta aquí**: el trigger bloquea todo
  UPDATE/DELETE de la tabla `confidence_scores` — incluso el ciclo de vida. Una
  recalibración con distintos inputs (p. ej. otra α o historia ECE) produce una
  fila nueva, nunca una edición. La UI lo comunica explícitamente.
- **El desglose del target reutiliza el store de Hypotheses**: el detalle de
  una calibración sobre una hypothesis resuelve anomalies + Active Contexts
  reusando `HypothesisReadStore.get_hypothesis` — cero lógica duplicada y la
  vista Confidence se apoya en la vista Hypotheses para explicar qué se está
  evaluando.
- **0 confidence_scores reales = empty state honesto**: el calibrator solo
  emite filas cuando el pipeline produce juicios (hypotheses primero), y el
  tenant sandbox aún no tiene hypotheses/anomalies reales. La vista muestra
  "No confidence yet" sin fabricar datos (P1). El desglose con datos reales se
  cubre con fakes en los tests (patrón `_ConfidenceStore`).

## Decisions & Trade-offs

- **Filtro por facets reales** (como Fases 3–8): el UI no inventa opciones de
  `target_type`; solo muestra los que el tenant tiene de verdad (hoy:
  `hypothesis`; recommendation/decision son capas futuras, R4).
- **Desglose por tipo de target**: hypothesis → desglose de Hypotheses
  (anomalies + contexts); decision/recommendation → payload canónico de la capa
  Action. La UI discrimina por `target_type` con componentes dedicados.
- **Nota P5 en el drawer**: la confianza se presenta siempre como estimación
  calibrada de fiabilidad, nunca como probabilidad de verdad — y se recuerda
  que cada campo se asignó al computarse y es inmutable.
- **Sin fase "Insights" inventada**: el roadmap canónico tras Confidence es
  Recommendations → Decisions; no se añadió una sección de navegación que no
  esté en el plan (política de no inventar fases).
