# 2026-08-25 — Fase 1: slice vertical end-to-end (producto_1.md)

## Objetivo
Aplicar el prompt `producto_1.md`. Su prioridad mandatoria (Fase 1) es una
**rebanada vertical demostrable de extremo a extremo** REALITY → OBSERVATION →
EVIDENCE → ACTIVE CONTEXT → PATTERN → ANOMALY → HYPOTHESIS → CONFIDENCE →
RECOMMENDATION → DECISION → REPORT, para salud de infraestructura Linux. El
prompt prohíbe iniciar fases siguientes hasta que la Fase 1 esté terminada y
demonstrable.

## Hallazgo
La plataforma **ya implementa** la cadena cognitiva completa como microservicios
autónomos encadenados por la base de datos. El artefacto verdaderamente ausente
que el prompt exige explícitamente (§22) era **un único pytest que recorre toda
la cadena** con aserciones de trazabilidad y aislamiento de tenant — solo existía
como script manual (`scripts/qa_seed.py`). Por tanto el entregable concreto de
Fase 1 fue esa prueba de integración automatizada y verificable.

## Trabajo realizado
- **`tests/integration/test_cognitive_pipeline_e2e.py`** (nuevo) — conduce los
  libs/contratos cognitivos **reales en proceso** (sin levantar los 12
  microservicios) contra PostgreSQL real. Tres escenarios:
  1. **Happy path**: 9 observaciones Linux CPU/MEM/DISK Q1 →
     `resource_exhaustion_evidence` → Context por competencia de coherencia
     (`resource_pressure`) → Pattern → Anomaly → ≥2 Hypothesis competidoras →
     Confidence (S+C+ECE ≈ 0.85) → Recommendation → Decision (commit grabado).

     `Decision → Recommendation → Hypothesis → Anomaly → Context → Evidence →
     Observations` resuelven y comparten el mismo `tenant_id`; dos tenants no se
     ven sus artefactos (R1/P1 scope).
  3. **R4 / sin acción sin confianza**: `calibrate` rechaza evidencia vacía;
     `commit` devuelve `None` cuando `confidence_score < 0.75` (gate de
     compromiso).
- **Lint**: se corrigió ruff en el nuevo archivo — `# ruff: noqa: E402` a nivel

  (B905), `list(...)` en vez de comprensión (C416), variable no usada (F841), y

## Cierre oficial de Fase 1 (remediación de CI)

Al publicar en GitHub (branch `feature/phase1-vertical-slice-e2e`, PR #1) el
pipeline fallaba en dos gates por deuda **pre-existente y ajena a Fase 1**
(ninguno tocaba el entregable de Fase 1: el e2e ya pasaba). Se corrigieron
para poder cerrar con CI verde:

1. **Root tests** — `ModuleNotFoundError: No module named 'src.boundary'` en
   `tests/security/adversarial/` (test_02/03/14/15). Causa raíz: dos apps
   (`context-service`, `gateway`) exponen un paquete de nivel superior llamado
   `src` (paquetes regulares con `__init__.py`); en la corrida raíz de `pytest
   tests/` colisionan bajo un mismo namespace y solo uno resuelve. Fix:
   convertir esos dos `src` en *namespace packages* (eliminar los
   `__init__.py`, que solo eran docstrings) y añadir `tests/conftest.py` que
   inserta `apps/gateway/api-gateway` en `sys.path`. Así `src` fusiona ambas
   porciones y `src.activator` (e2e) y `src.boundary`/`src.service`
   (adversarial) conviven sin orden-dependencia. Sin cambio de comportamiento
   de producto.

2. **Service tests** — `decision-service`:
   `test_decision_save_is_idempotent` → `assert 325 == 1`. Causa raíz:
   `DecisionService.run_decision_cycle` operA de forma **global** (no
   acotada por tenant), por lo que `total_duplicates` y los conteos se
   contaminan con datos dejados en el Postgres compartido por otras suites
   (p.ej. el e2e de Root tests siembra muchos tenants). Fix acotado a la
   prueba: truncar las tablas cognitivas al inicio del test para un estado
   limpio y determinístico. Sin cambio de comportamiento de producto.

## Nota de trazabilidad A3 (producto_4.md) — decisión arquitectónica

`producto_4.md` A3 exige como aserción obligatoria `assert report.decision_id
== decision.id`. Tras inspección (`libs/action/report.py`) se confirma que el
modelo `Report` y la tabla `reports` **no tienen** columna `decision_id`. La
trazabilidad vive en `content["decision_traces"]` (una entrada por decisión).

**Inconsistencia arquitectónica detectada (REGLA FINAL):** un `Report` periódico
agrega *N* decisiones de un tenant en un periodo (relación 1:N, ADR-0002: el
Report es salida no canónica que formatea lo ya comprometido). Un `decision_id`
singular sería semánticamente incorrecto y, además, añadir una columna/ FK nueva
viola A9 (el diff de cierre solo admite el E2E, ajustes de test requeridos,
documentación y comportamiento de CI — no nuevos esquemas de BD).

**Resolución:** se verifica la trazabilidad mediante el mecanismo canónico
`content["decision_traces"]`, que es estrictamente más correcto que un FK
singular. Se añadió en el E2E (`tests/integration/test_cognitive_pipeline_e2e.py`):

```python
assert any(
    t["decision"]["id"] == str(d.id) for t in report.content["decision_traces"]
)
```

más el recorrido completo `Report → Decision → Recommendation → Confidence →
Hypothesis → Anomaly → Context → Evidence → Observation` usando los `id` reales
de la traza. Esto satisface el *propósito* de A3 (Report→Decision resoluble) sin
introducir un cambio arquitectónico incorrecto ni un nuevo campo de BD.
